## 1. Objective

Add a credible, honest quantum-computing use case inside EasyClaim's SCREENING stage: a quantum-kernel one-class anomaly signal, compared against a classical baseline on identical features, exposed to assessors as advisory context and kept outside every security control.

## 2. Why quantum belongs in Screening

Screening is the only stage whose job is to enrich a claim with signals for a human. Authentication, authorization, the state machine, decisions and payouts are deterministic controls (Phases 0–3) where an experimental model has no business. A screening signal can be wrong without breaking a security guarantee, because it only informs the assessor who still performs `Screening → Review` themselves. This matches the master plan §10 and §19.

## 3. Why one-class anomaly detection was selected

The repository has **no fraud labels** (`PHASE_04_PRECHECK.md` §6). A supervised quantum classifier would have required fabricating labels, which the master plan forbids. A one-class model learns what the reference claim population looks like and scores how dissimilar a claim is. It needs no labels, so the comparison with the classical baseline is fair and the result cannot be inflated by invented ground truth. The teammate's quantum-optimisation proposal (assessor prioritisation) is recorded as future research; it is an operations problem that needs a risk signal as input rather than a replacement for one.

## 4. Available data

| Source | Rows | Use |
|---|---|---|
| `seed_sa_data.sql` demo claims | 3 | scored with the real schema; incident dates and categories are NULL, so features are imputed |
| `quantum/data/dev_claims.json` | 120 synthetic normal + 16 synthetic anomalies | reference population and evaluation; **SYNTHETIC, generated by `dataset.py` with seed 4** |

Anomaly recipes (labelled, never presented as fraud): `late_report` (4: reported 180–400 days after the incident), `serial_claimant` (8: one user id with eight claims), `night_minimal_narrative` (4: created 02:00–04:00 with a 1–3 word narrative).

## 5. Features (5 → 5 qubits)

`days_to_report`, `category_index`, `prior_claim_count`, `narrative_word_count`, `submission_hour`. All derived from columns that exist today (`quantum/easyclaim_quantum/features.py`). Not available and not fabricated: amount, policy age, evidence count, geography.

## 6. Preprocessing (shared by both models)

Fit on the synthetic normal rows only. Median imputation (`[6.0, 1.0, 2.0, 25.0, 12.0]`), `log1p` on `days_to_report`, `prior_claim_count`, `narrative_word_count`, min-max on the reference range, then a soft clip into [0, 1]: the reference range maps to [0, 0.75] and values above the reference maximum are compressed into (0.75, 1) with `1 − exp(−(s − 1))` so extreme values keep their order instead of being flattened. Angles for the quantum map are `x · π`. Exact parameters are in `results.json → preprocessing`.

## 7. Classical baseline

`sklearn.svm.OneClassSVM(kernel='rbf', gamma='scale', nu=0.1)` on the scaled matrix. Raw score = negated signed distance to the boundary.

## 8. Quantum kernel

Framework: PennyLane 0.45.1, device `default.qubit` (statevector simulator). Kernel `k(x, y) = |⟨φ(y)|φ(x)⟩|²`. Computed once per claim as a statevector (139 circuit simulations) and combined algebraically; six random entries were cross-checked against the adjoint-overlap circuit (`U(x) U(y)†`, probability of `|00000⟩`), maximum absolute difference 0.00e+00. Kernel validation on the 120×120 reference matrix: symmetric, unit diagonal, entries in [0, 1], positive semidefinite (minimum eigenvalue 1.80e−16).

## 9. Quantum feature map

Per repetition (2 repetitions): `H` and `RZ(x_i)` on each of the 5 wires, then for neighbouring wires `(i, i+1)`: `CNOT`, `RZ(x_i · x_{i+1} / π)`, `CNOT`. First-order plus nearest-neighbour second-order encoding; the `/π` keeps the two-qubit phase in [0, π] to avoid kernel concentration on a five-feature problem.

## 10. Model architecture

`OneClassSVM(kernel='precomputed', nu=0.1)` fitted on the quantum kernel of the reference rows; scored on the kernel between each claim and the reference rows. Both models' raw scores are converted to a percentile against the reference population, so scores are comparable: 0.80 means "more anomalous than 80% of reference claims". Bands: `NORMAL < 0.80 ≤ UNUSUAL < 0.95 ≤ HIGH_ANOMALY`. By construction 20% of the reference population lands at UNUSUAL or above and 5% at HIGH_ANOMALY; these bands are a screening heuristic and not a fraud threshold.

## 11. Experiment results (simulator)

| Metric | Classical (RBF) | Quantum kernel |
|---|---|---|
| Synthetic anomalies inside the model's top-16 | 9 / 16 | 8 / 16 |
| `late_report` (4) flagged ≥ UNUSUAL | 4 | 4 |
| `serial_claimant` (8) flagged ≥ UNUSUAL | 2 | 3 |
| `night_minimal_narrative` (4) flagged ≥ UNUSUAL | 4 | 1 |
| Mean score, reference rows | 0.504 | 0.504 |
| Mean score, synthetic anomalies | 0.814 | 0.798 |
| Fit + score runtime | 0.018 s | 1.885 s |

Agreement between the models: Spearman rank correlation of raw scores 0.837; overlap of the two top-16 sets 0.4375.

Seed demo claims (real schema, imputed features): `claim_disc_101` 0.77 / 0.54 NORMAL, `claim_sanlam_102` 0.77 / 0.54 NORMAL, `claim_mom_103` 1.00 / 0.70 NORMAL (classical / quantum). Their features are almost entirely imputed, so these numbers demonstrate the pipeline, not the claims.

**Reading of the result.** Both models find the late-report recipe every time. The classical baseline is clearly better on the night-time minimal-narrative recipe. The quantum kernel is marginally better on the serial-claimant recipe, which both models mostly miss because eight claims for one user is still close to the reference maximum of two prior claims after log scaling. Overall the quantum-kernel model does **not** outperform the classical baseline on this synthetic data, and it is about 100× slower on a simulator. This is the measured result.

## 12. Simulator / hardware used

Simulator only: PennyLane `default.qubit`, Python 3.13.15, Windows 11. **Real hardware: NOT USED.** No IBM Quantum or other credentials were available or requested; the code path that a shot-based backend would run (`kernel_entry_circuit`) exists and is tested against the statevector path. Every stored signal has `execution = 'simulator'`.

## 13. Limitations

- Synthetic reference population; percentiles are relative to it, not to real traffic. Real data would require re-fitting and a decision on `nu`.
- Five weak features; no amount, no evidence, no policy age. `prior_claim_count` is computed within the scored population.
- `category_index` is ordinal, which imposes an arbitrary ordering on categories.
- Statevector simulation is exact; hardware would add shot noise and device error, and a full 120-row kernel would need 23,460 circuit executions.
- Reference rows are scored in-sample, which makes their scores slightly optimistic for both models equally.
- The pipeline runs offline. There is no scheduled or event-driven scoring; signals for new claims must be imported by an operator.

## 14. Security boundary

- No API route writes `screening_signals`. `POST /screen` ignores request bodies; the customer screening schema is `.strict()` and rejects a `quantumAnomaly` field with 400. `POST/PUT/PATCH/DELETE /risk-signals` do not exist (404).
- Reads go through `requireActor → requireRole(ASSESSOR, MANAGER) → loadAuthorizedClaim('insurer')`. Cross-tenant → 404, customer → 403, no token → 401 (tests and live log).
- Database `CHECK` constraints reject scores outside [0, 1], bands other than the three, and any `execution` other than `simulator`/`hardware`. `claim_id` references `claims(id)`.
- The signal is attached **after** `transitionClaim` returns and is never read inside it. A `HIGH_ANOMALY` row leaves the `claims` row byte-identical (test `screeningSignals.test.ts`). `Screening → Review` still requires the assessor's call.
- The Worker never imports Python or calls out to a quantum service; there is no new network egress.
