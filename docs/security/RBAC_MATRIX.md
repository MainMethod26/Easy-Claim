# RBAC Matrix

## What exists in code

- The roles `CUSTOMER`, `ASSESSOR`, `MANAGER`, `ADMIN` are the `Role` type in `src/types.ts` (`ROLES`; `INSURER_ROLES = ['ASSESSOR','MANAGER']`). The actor is `{ id, role, tenantId: string | null }`.
- **Phase 1 update: roles now come from verified token claims.** `resolveActor` (`src/security/actor.ts`) verifies `Authorization: Bearer <JWT>` with `hono/jwt` `verify` (HS256 pinned, `iss` = `JWT_ISSUER`, `aud` = `JWT_AUDIENCE`) and `validateClaims` maps `sub` → `actor.id`, `role` → `actor.role` (must be in `ROLES`) and `tenant_id` → `actor.tenantId`; `exp` and `iat` are required and the remaining lifetime is capped per role. The Phase 0 `X-Dev-Actor-*` header stub and `ALLOW_DEV_ACTOR_HEADERS` are REMOVED. There is still **no identity provider and no user or role store**: whoever holds `JWT_SECRET` decides which role and tenant a token carries (locally `scripts/mint-token.mjs`; an external IdP via `hono/jwt` `verifyWithJwks` is PLANNED, not implemented). No revocation exists (PLANNED).
- Enforcement lives in four places:
  - `requireActor` (`src/index.ts` on `/api/v1/*`; `src/security/actor.ts`)
  - `requireRole(...)` (`src/security/rbac.ts`) — coarse and resource-independent, applied before any claim lookup so a 403 never reveals whether a claim exists or which tenant owns it
  - `loadAuthorizedClaim(c, id, 'read' | 'owner-write' | 'insurer')` (`src/security/claimAccess.ts`) — decision order load → tenant boundary → ownership → mode. `isTenantInsurer()` requires an insurer role AND `actor.tenantId === claim.tenant_id` (non-null) AND `claim.stage !== 'Draft'`. Denied and missing both return 404 `{"error":"not_found"}` and write `authz.claim_access_denied` `{mode, exists, reason}` (reasons: `missing`, `not_owner`, `cross_tenant`, `tenant_unset`, `draft`, `role`, `mode`, `transition_guard`).
  - `transitionClaim(c, claim, to, opts)` (`src/security/claimAccess.ts`) — re-asserts owner / tenant insurer (403 + audit), then `checkTransition(from, to, actor.role)` (`src/security/claimStateMachine.ts`) for the legal edge and the per-transition role (403 `forbidden` / 409 `illegal_transition`, audited `claim.transition_rejected`), then ONE D1 batch: `UPDATE ... WHERE id = ? AND stage = ?` plus the audit `INSERT ... WHERE changes() = 1`; 0 rows → 409 `stale_state` (audited).
- **Tenant/org scoping is IMPLEMENTED (Phase 1).** `tenants` table plus `policies.tenant_id` and `claims.tenant_id` (`migrations/0003_tenants.sql`; seed tenants `ins_discovery`, `ins_sanlam`, `ins_outsurance`, `ins_momentum`, `ins_oldmutual`). `POST /claims/initiate` copies `tenant_id` from the policy; a policy without a tenant is not eligible (422, audited `policy_missing_tenant`). Insurer staff belong to exactly one tenant (the `tenant_id` claim) and can only see or act on that tenant's non-Draft claims. Customers are platform-level (no tenant: seed `user123` holds Discovery, Sanlam and Old Mutual policies) and are matched by ownership (`claims.user_id`).
- **ADMIN has no claim powers** by design: no transition in `TRANSITIONS`; `GET /claims` → 403 (audited `authz.role_denied`); the two read routes `GET /claims/:id/timeline` and `/decision` → 404 (audited `authz.claim_access_denied` reason `role`; `timeline` is TESTED/PASSED in `rbac.test.ts` "admin has no claim-reading powers" and `tenant.test.ts` TENANT-001b, `/decision` follows the same `loadAuthorizedClaim(..., 'read')` path but has no ADMIN-specific test — NOT TESTED directly); every role-gated route (customer writes, insurer transitions, `/ocr/process`) → 403 from `requireRole` before any claim lookup (`tenant.test.ts` TENANT-001b, RBAC-002). ADMIN-only functions (config, roles) still do not exist. **ADMIN semantics: DECISION REQUIRED** — `tenant_id` is optional in an ADMIN token and is not used in any authorization decision (it is only recorded in `audit_events.actor_tenant_id`); platform admin vs tenant admin is undecided.
- **Separation of duties: DECISION REQUIRED.** The same MANAGER may `decide` and then `pay` the same claim; no decider ≠ payer check exists in code. There is also no "must not be the original decider" check on appeal review and no appeal count limit (DECISION REQUIRED).

## Token claims per role (Phase 1)

Enforced by `validateClaims` in `src/security/actor.ts`; a violation is a 401 with the fixed reason token logged (never the claims).

| Role | `tenant_id` claim | Max remaining lifetime (`MAX_TOKEN_TTL_SECONDS`) | Claim access basis | Enforced in |
|---|---|---|---|---|
| CUSTOMER | **forbidden** (reason `customer_with_tenant`) | 24 h | Ownership: `claims.user_id === sub` | `actor.ts` `validateClaims`; `claimAccess.ts` `loadAuthorizedClaim` (`isOwner`) |
| ASSESSOR | **required** (reason `staff_without_tenant`) | 8 h | Tenant: `claims.tenant_id === tenant_id`, stage ≠ Draft | `actor.ts` `validateClaims`; `claimAccess.ts` `isTenantInsurer` |
| MANAGER | **required** | 8 h | Tenant, plus MANAGER-only transitions (`Decision → Paid`, `Appeal → Review`) | as ASSESSOR, plus `claimStateMachine.ts` `TRANSITIONS` |
| ADMIN | **optional** (DECISION REQUIRED) | 8 h | None: no claim access, no transitions | `rbac.ts` `requireRole` (403 on every role-gated route); `claimAccess.ts` `loadAuthorizedClaim` (404, reason `role`, on the read routes); `claims.ts` `GET /` (403) |

"PLANNED" means the rule is defined here but has no endpoint yet; "PARTIAL" means only part of the row's rule exists in code.
